# VoiceGateway Strategic Audit

**Date:** 2026-05-02 (synthesis: 2026-05-03)
**Scope:** Read-only diagnostic on a published, in-production product (PyPI `voicegateway==0.0.3`, Docker Hub `mahimairaja/voicegateway:latest`, Fly.io one-command deploy, docs at `vg.openrtc.tech`).
**Bar:** Not "is the architecture good?" but "is this product ready to grow 10x in users?"

---

## Executive summary

- **Maturity grade: C+ (work-in-pilot).** The codebase is clean and the artifact set is launch-ready (60-page docs, multi-arch Docker, Fly script, MCP server, dashboard, CI), but it is two and a half weeks past first commit, has 1 human contributor, three releases, and zero stars. Functional for self-hosted single-instance pilots, not production-multi-tenant.
- **Wedge strength: 5/10 — real but narrower than the README claims.** Cost tracking and budget enforcement are solid engineering, not a moat — LiteLLM does this at parity. The genuine differentiation is *LiveKit-native return types + modality-aware unit accounting + agent-managed config via MCP*, and it survives only inside the LiveKit voice-agent niche.
- **Top growth bottleneck hypothesis: distribution / awareness, with stale wedge framing as a close second.** 0 GitHub stars, 0 issues, 0 forks, 0 external mentions in HN/Reddit/Twitter — despite a polished launch surface — points squarely to "no launch happened yet." The framing slip (`docs/migration/from-litellm.md:12-19` still claims LiteLLM has no STT/TTS, which is stale as of May 2026) compounds it on first contact with sophisticated readers.
- **Top recommendation: launch publicly with a tightened, voice-agent-specific narrative within 2 weeks** — Show HN + r/voiceai/r/livekit posts + a blog post, paired with a README rewrite that leads with "the gateway your LiveKit voice agent needs" and a fixed migration doc. This is 1-2 person-weeks of work with low risk and the highest possible ratio of upside to effort given current adoption.
- **Most surprising finding: VoiceGateway has no `/v1/chat/completions` OpenAI-compatible HTTP endpoint.** Verified by grep — `server.py` (599 lines) exposes `/v1/status`, `/v1/costs`, `/v1/models`, `/v1/projects`, `/v1/logs`, `/v1/audit-log`, `/v1/metrics`, but no inference proxy endpoint. The product is a *Python library* (returns LiveKit plugin instances) wrapped in an *admin API*; it is not an HTTP gateway in the LiteLLM sense at all. This is fine for the LiveKit niche but invisible from the README, which calls itself "an inference gateway" — a phrase that primes readers to expect a proxy.

## Section 2 — Cost tracking deep-dive (the wedge)

This section gets the most space because cost tracking is the positioned differentiator. Verdict at the bottom: **solid engineering, table-stakes — not a moat.**

### 2a. Cost calculation mechanics

Cost is computed synchronously after each request in `CostTracker.calculate_cost()` (`voicegateway/middleware/cost_tracker.py:35-63`):

```python
if modality == "stt":
    return input_units * pricing.get("per_minute", 0.0)
elif modality == "llm":
    input_cost = input_units * pricing.get("input_per_1k", 0.0) / 1000
    output_cost = output_units * pricing.get("output_per_1k", 0.0) / 1000
    return input_cost + output_cost
elif modality == "tts":
    return input_units * pricing.get("per_character", 0.0)
```

The unit basis is **modality-correct** and not generic-token-based — STT is per-minute, LLM is per-1k tokens (input/output split), TTS is per-character. This matches actual provider billing and is one of the few places VG genuinely improves on LiteLLM's text-token model.

**Pricing source.** Hard-coded Python dict in `voicegateway/pricing/catalog.py` — 9 STT entries, 10 LLM entries, 6 TTS entries. There is no pricing lookup against a provider API, no remote sync, and no mtime-stamped record of when the table was last validated.

**Pricing freshness:** the file has only ever been touched by the initial commit (`2026-04-13`). At 20 days old as of audit, today's prices likely match published rates (spot-check: `openai/gpt-4o` at `$0.005/$0.015` per 1k matches OpenAI's site; `anthropic/claude-3.5-sonnet` at `$0.003/$0.015` matches Anthropic's). The *level* of freshness today is fine. The *mechanism* is the concern: there is no playbook, no test, no CI step, and no alert that fires when a provider changes prices. The first time someone changes a price between releases, VG will be silently wrong about cost. Provider count = 11; cadence of provider price changes ≈ monthly across the basket → expected drift events ≈ 1/month. Without instrumentation this drift accumulates.

**Notable gaps:**
- `groq/llama-3.1-8b` is hard-coded at `$0.0`. Groq's free tier has rate limits and isn't actually free at production volume — this will under-report cost for any real Groq workload.
- Only 6 TTS models are priced. Cartesia + ElevenLabs both publish per-voice pricing tiers; VG collapses every voice to one rate.
- No `mtime` or `source_url` metadata in the catalog; reconciling against a provider invoice means manually checking the dict against each provider's pricing page.

**Streaming responses.** Costs are calculated from `input_units` and `output_units` that the caller passes in. The instrumented provider (`voicegateway/middleware/instrumented_provider.py:61-107`) wraps STT/LLM/TTS objects and computes these post-hoc — but there is no special path for streaming vs batch. For LLM streaming, this works *if* the wrapper sums tokens across chunks before logging; for streaming STT (duration-based), it depends on the wrapper grabbing the audio length. None of this is unit-tested for streaming-specific scenarios — `tests/middleware/test_cost_tracker.py` tests the formula, not the streaming bookkeeping.

**Failed calls.** `RequestRecord` carries a `status` field (default `"success"`) and `error_message` (`voicegateway/storage/models.py`). A failed request is still logged with its cost calculated from whatever `input_units` were known at failure time. This is reasonable but not configurable — a user who wants "don't charge me for 5xx errors" cannot express that.

**Retries.** A grep for `retry|backoff` across `voicegateway/` returns zero hits. **VoiceGateway itself does not retry.** The cost-double-charging concern that a naive read suggests is real *only* for retries inside the underlying provider SDK (e.g., LiveKit's deepgram plugin), and those retries are invisible to VG. The fallback chain (`voicegateway/middleware/fallback.py`) switches to a *different* provider on failure — that's a different cost, not a duplicate of the same cost. So in current code: no double-billing risk from VG's own logic.

### 2b. Budget enforcement

Project definition (`voicegateway/core/config.py`, schema `voicegateway/core/schema.py:43-49`):
```python
class ProjectConfig(_StrictBase):
    name: str
    daily_budget: float = 0.0
    budget_action: str = "warn"  # warn | throttle | block
    tags: list[str] = []
    default_stack: str = ""
```

Project tag flows through to a request via the `project=` argument on `gw.stt()/llm()/tts()` (per `examples/budget-enforcement.md`). Default project is `"default"` (`voicegateway/core/gateway.py:26`).

**Granularity:** per-project, daily window only. There is no per-modality budget, no per-model budget, no monthly window, no custom date range. For a 50-person startup that wants "marketing-bot can spend $20/day on STT but unlimited LLM," there's no expression for that today.

**Three actions** (`voicegateway/middleware/budget_enforcer.py:185-201`):
- `warn` — log and proceed.
- `throttle` — raise `BudgetThrottleSignal`; the caller is expected to fall back to local stack.
- `block` — raise `BudgetExceededError`; the request is rejected.

**Latency cost on the hot path.** Budget check goes through `_get_today_spend()` (`budget_enforcer.py:84-109`) which is cached in memory with a 30-second TTL (`cache_ttl_seconds=30.0`, line 59). Hot path with cache hit: ~microseconds (dict lookup under an asyncio lock). Cache miss: a single SQLite SUM query (cost is bounded by SQLite read latency, typically <5ms on local disk, can be 20-100ms on shared volumes). For voice agents this is well-amortized — only one of every ~30s × QPS requests pays the miss cost.

**Race conditions.** The implementation is unusually careful for a 3-week-old codebase:
- **Per-project `asyncio.Lock`** (`budget_enforcer.py:69-71, 76-82`) prevents two coroutines from racing on the same project's cache read-modify-write. A single global lock would be simpler but would serialize unrelated projects, so this is the right tradeoff.
- **Optimistic spend update via `record_spend()`** (lines 111-148) closes the TTL blind spot: when a request lands its cost into storage, the cached value is incremented immediately so the *next* request for the same project sees the freshly-spent amount.
- **Timestamp comparison** (lines 144-147) prevents a double-count when a concurrent cache refresh has already pulled the row in: `if ts >= logged_at: return`.
- Test coverage for this is in `tests/middleware/test_budget.py:165-260` (cache coalescing, optimistic update, double-count avoidance).

This is good in-process design. The remaining 30-second TTL window can still allow a small overshoot during a burst — bounded by `(burst_qps × 30s × cost_per_request)`. For a $5/day project on a stack averaging $0.001/request, the overshoot is sub-cent. For a $5/day project on a $0.05/request stack at 100 qps, you can overshoot by $150 in 30 seconds, blowing the daily budget 30x. So the small-overshoot story is workload-dependent; the docs don't quantify it.

**Multi-instance — the structural ceiling.** Two VG processes pointing at the same SQLite file have *independent in-memory caches.* Neither sees the other's optimistic updates until its own 30-second TTL expires. This is the horizontal-scaling cliff: the engineering inside one process is careful, but the moment a user runs N instances behind a load balancer, budget enforcement becomes "best effort within ~30 × N seconds" — and there is no shared cache layer (Redis, Memcached) wired in. Today this is acceptable because the only documented topology is single-instance Fly/Docker/local. It becomes the dominant correctness issue the day VG tries to scale past one node, and there is currently no plan in the code or roadmap for it.

### 2c. Reporting and reconciliation

The HTTP surface is `GET /v1/costs` (`voicegateway/server.py:140-144`), accepting `period=today|week|month` and optional `project=`. Returns aggregate sums plus `by_provider` and `by_model` dicts. No per-request drilldown, no custom date range, no per-modality split (STT vs LLM vs TTS), no per-project comparison.

The dashboard *does* exist (the cost-deep-dive agent originally said it didn't — that was wrong) and lives at `dashboard/frontend/src/pages/Costs.tsx`. It renders total spend, two charts (by provider, by model), and a table of (model, requests, cost). What it does *not* have:
- A time-range picker (the page just hits `/api/costs` with no parameters per `Costs.tsx:12`).
- A project filter (the dropdown is a global concept; on this page it's not exposed).
- An export button.
- A drilldown view linking from a model row to the underlying requests.

A grep for `csv|export|download` across `voicegateway/` returns zero matches in cost-related code. There is no CSV export, no JSON download endpoint, no scheduled report.

**Reconciliation against provider invoices: nothing.** No tooling, no docs page, no CLI command. A CFO who wants to verify VG's number against the OpenAI invoice would need to dump SQLite manually with `sqlite3 ~/.config/voicegateway/voicegw.db "SELECT * FROM requests WHERE provider='openai' AND date(timestamp,'unixepoch') = date('now','-1 month')"` and reconcile by hand. This is the largest gap in the wedge.

**No forecast / no projection.** `/v1/costs` returns historical totals only.

### 2d. Honest assessment

The cost tracking *engine* is solid, careful, modality-aware, and concurrency-safe within one process. It is not a thin SQL counter — the per-project locking, optimistic cache updates, and timestamp-based double-count avoidance reflect a real engineering pass. Praise where due.

But the *product surface* of cost tracking is shallow. The reporting endpoint returns aggregates only. The dashboard has no filters or drilldowns. There is no CSV export. There is no reconciliation tooling. The pricing table has no source-date metadata or refresh mechanism. The budget granularity is one knob (project × daily). For a CFO at a 50-person startup the question "show me last month's spend by week, by provider, with a column for what we expected vs what we paid the provider" cannot be answered from VG today — they would write a script.

**Versus LiteLLM:** LiteLLM has multi-level budgets (personal / team / key / model / agent), multiple time windows, TPM/RPM, and an admin UI with broader filters. LiteLLM's per-modality cost tracking is weaker (token-centric), but its overall reporting is broader. The honest scorecard: VG wins on modality-aware unit accounting; LiteLLM wins on granularity, time windows, multi-instance reality, and reporting depth.

**Bottom line: cost tracking is well-engineered table-stakes, not a defensible moat.** The defensibility, if there is any, is the *combination* of (a) modality-aware unit accounting + (b) project-tagged enforcement + (c) MCP tools that let a coding agent set budgets conversationally — none of which LiteLLM combines today. Lead with the combination, not "cost tracking" alone.

## Section 3 — Other capabilities

### 3a. Fallback & resilience

Files: `voicegateway/middleware/fallback.py`, `voicegateway/core/router.py`, `voicegw.example.yaml:148-162`, `tests/middleware/test_fallback.py`.

Chains are defined globally per modality in YAML (`stt: [deepgram/nova-3, groq/whisper-large-v3, local/whisper-large-v3]`, etc.). Per-project fallback is not configurable; per-request override is not configurable. This is a real limitation if "premium" project should have a different chain than "budget" project.

**The structural issue:** failover triggers only on **resolver failure** in `Router.resolve()` (`router.py:43-102`), not on runtime errors during a call. A user reading the README's "Cloud outage? Switch to local. Your agent keeps running." (verbatim from `docs/index.md:48`) would expect that a Deepgram outage *during* an active phone call triggers failover to Groq Whisper mid-call. It does not — once the resolved provider is wired into the LiveKit `AgentSession`, runtime errors propagate to the user, not to a fallback handler. The fallback chain is for *startup* resolution failures, not *operational* failures. This is the most overstated claim in the marketing copy.

There is no circuit breaker, no consecutive-failure detection, no per-attempt timeout, and no jitter/backoff. A flapping provider is retried on every request. Tests in `test_fallback.py` cover happy path, error-driven advancement, exhaustion, and callback wiring — but only at the resolver level.

**Maturity: 5/10.**
**Solid:** Per-modality config, exception-driven chain, callback hook, comprehensive resolver-level tests.
**Rough:** Resolver-only (not runtime), no circuit breaker, no per-attempt timeout, no per-project chains, README oversells it.

### 3b. Observability

Files: `voicegateway/middleware/latency_monitor.py`, `voicegateway/middleware/instrumented_provider.py`, `voicegateway/storage/_percentiles.py`, `voicegateway/storage/sqlite.py`, `voicegateway/server.py`.

Every provider instance is wrapped by `InstrumentedSTT|LLM|TTS` (`instrumented_provider.py:110-126`). `time.perf_counter()` is captured at call start (`:42`), `_mark_first_byte()` is called on first response chunk (manual hook), and `_log_request()` writes to SQLite at end. Percentiles are computed in `_percentiles.py:27-77` with linear interpolation matching `numpy.percentile(method='linear')` — correct for Prometheus/Grafana parity.

`/v1/metrics` is Prometheus text format (per recent commit `5328b4e: feat: per-model latency percentiles + Prometheus summaries`). Prometheus Summaries expose p50/p95/p99 per model. There is no OpenTelemetry exporter, no Datadog/Honeycomb integration, no log aggregation hook — the data is in SQLite + Prometheus and nowhere else. For users on Datadog/Honeycomb stacks, they have to scrape Prometheus and forward, which is an extra step that's not documented.

The `_mark_first_byte` callback is **manual**: if the wrapper code forgets to invoke it for a new modality, TTFB silently equals total latency and no test catches it. Pre-aggregated percentile rollups don't exist; percentile queries scan the `requests` table on every dashboard render.

**Maturity: 7/10.**
**Solid:** Microsecond timing, correct percentile math, Prometheus surface, modality-aware schema.
**Rough:** Manual TTFB hook, no pre-aggregation, no OTel/Datadog export, error data limited to `error_message` text (no classification).

### 3c. Local model serving

Files: `voicegateway/providers/{whisper,kokoro,piper,ollama}_provider.py`.

Whisper uses `faster-whisper` (CTranslate2 backend, not torch). Device is config-driven via `device: auto|cpu|cuda` and `compute_type: float16|float32` in `voicegw.yaml`. Kokoro loads ONNX models async via `asyncio.to_thread`. Piper loads voices from `~/.local/share/piper-voices/`. Ollama is an HTTP client to `localhost:11434`.

**The limitation that matters at scale:** there is no warm-pool, no LRU eviction, no memory tracking. Loading Whisper-large-v3 (~3GB), Kokoro (~1GB), and Piper voices (~0.5GB each) onto a shared GPU will OOM with no graceful degradation. There is no per-model load timing surfaced in metrics, so users can't easily measure "what's my cold-start cost for swapping from cloud Whisper to local Whisper?" The README claims "Cloud outage? Switch to local. Your agent keeps running" — true *if* the model is already loaded, but cold load time is real (5-30s on first use).

The Ollama integration is the cleanest of the four because Ollama itself handles model lifecycle.

**Maturity: 5/10.**
**Solid:** Lazy load, async wrapper, four engines covered, Ollama-as-supervisor pattern.
**Rough:** No memory budget, no LRU/unload, cold-start cost not measured or surfaced, GIL bottleneck on CPU-only Whisper.

### 3d. MCP server (17 tools)

Files: `voicegateway/mcp/server.py`, `voicegateway/mcp/auth.py`, `voicegateway/mcp/schemas.py`, `voicegateway/mcp/tools/{models,projects,providers,observability}.py`.

The 17 tools (per file inventory):
- **Observability** (5): `get_health`, `get_provider_status`, `get_costs`, `get_latency_stats`, `get_logs`.
- **Models** (~3-4): `list_models`, `get_model_info`, `add_managed_model`, `remove_managed_model` (estimated from file).
- **Projects** (~4): `list_projects`, `create_project`, `set_project_budget`, `delete_project`.
- **Providers** (~4): `list_providers`, `add_managed_provider`, `test_provider`, `remove_managed_provider`.

Transports: stdio (subprocess mode for Claude Desktop / Cursor / Codex) and HTTP/SSE (`/mcp` endpoint via FastAPI). Authentication on the HTTP/SSE transport is a **flat bearer token** via `VOICEGW_MCP_TOKEN` env var (`voicegateway/mcp/auth.py:22-45`). Constant-time comparison via `hmac.compare_digest`. Stdio transport is intentionally unauthenticated — local subprocess access is the trust boundary.

**Important fact-check:** the HTTP API at `/v1/*` (`voicegateway/core/auth.py`) has scope-based authorization (`require_scope("write")`), but the MCP HTTP/SSE auth is just a flat token — no scopes, no read/write split. A token holder can call `set_project_budget` (write) just as easily as `get_costs` (read). For agent-managed configuration, this is the right tradeoff (the token holder is "trusted to manage"), but it's a hard ceiling for any future "expose MCP to less-trusted clients" story.

There is no rate limiting on MCP HTTP/SSE (called out as a TODO in `TODO.md:14`). There is no audit log for tool calls — only the underlying CRUD ops on managed resources go through `config_audit_log`.

The intended use case is **agent-managed configuration** — Claude Code / Cursor / Codex managing a deployed VG. This is well-aimed: the README and docs lead with "manage VoiceGateway from your coding agent." Whether this is a *durable* differentiator depends on whether other gateways ship MCP — LiteLLM hasn't yet, but it's a few weeks of work for them when they choose to.

**Maturity: 6/10.**
**Solid:** 17 tools cover the operational surface, dual transport, constant-time auth, well-aimed UX (agent-managed config).
**Rough:** No scopes on MCP transport, no rate limits, no tool-call audit log, edges blur with HTTP API which has its own auth model.

### 3e. Encrypted key management

Files: `voicegateway/core/crypto.py`, `voicegateway/core/config_manager.py`, `tests/core/test_crypto.py`.

Fernet (AES-128-CBC + HMAC-SHA256) for managed provider API keys stored in SQLite (`managed_providers.api_key_encrypted`). The Fernet master key is loaded from:
1. `VOICEGW_SECRET` env var (highest priority).
2. `~/.config/voicegateway/.secret` file (mode 0600).
3. Generated on first run if neither exists.

The atomic-write fix called out in the conversation history (`os.open(O_CREAT|O_TRUNC, 0o600)` + `os.replace()`) addresses the temp-file-world-readable race that the capabilities-redo agent flagged from a static read.

**No key rotation.** No `MultiFernet` for key versioning, no `voicegw rotate-secret` command, no documented procedure for rotating the master key. If the key leaks, the user must (a) decrypt all managed keys with the old key, (b) generate a new key, (c) re-encrypt with the new key, (d) restart. None of this is automated.

**Recovery story:** if `~/.config/voicegateway/.secret` is lost and `VOICEGW_SECRET` is unset, *all managed provider keys are unrecoverable.* The user must re-add them via the dashboard or YAML. There is no warning about this in `docs/architecture/security.md` (existence of file noted in tree, content not read). For a self-hosted product this is acceptable; for a managed offering it would be a compliance issue.

**Maturity: 6/10.**
**Solid:** Fernet (vetted lib), env-var fallback, file-mode discipline, atomic write fix.
**Rough:** No rotation, no MultiFernet versioning, recovery story = "re-enter your keys."

## Section 4 — Developer experience

### 4a. Smallest "hello world"

Path from README → quick-start → first agent:
1. `pip install "voicegateway[cloud,dashboard,mcp]"` — 30-60s.
2. `voicegw init` (writes `voicegw.yaml`) — 5s.
3. Edit YAML to add `${OPENAI_API_KEY}` and `${DEEPGRAM_API_KEY}` (or set env vars) — 1-2 min.
4. `voicegw status` to verify providers — 5s.
5. Write 5-line script using `gw.stt(...)` returning a LiveKit STT instance — 30s.

For **just the library, no agent**: 3-5 minutes. World-class.

For **a working voice agent** (the actual product use case), add steps:
6. `pip install "livekit-agents"` and silero VAD — 30s.
7. Stand up a LiveKit server (`livekit-server` or LiveKit Cloud) and set `LIVEKIT_URL`/`LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET` — **10-30 minutes** (this is the real friction).
8. Wire `AgentSession` and run `python examples/basic_agent.py dev` — 5 min.

**Total: 15-35 minutes for working voice agent.** The bottleneck is LiveKit server setup, not VG. `docs/guide/first-agent.md` does not include LiveKit prerequisites in the prereqs section (per the DX/prod agent's read), which is a friction point for users new to LiveKit.

**Verdict: 6/10.** Library-only path is excellent; agent path is gated by LiveKit setup that the docs assume rather than walk through.

### 4b. API contract

VoiceGateway is **a Python library, not an HTTP gateway.** The public surface is exactly three exports (`voicegateway/__init__.py:7`): `Gateway`, `ModelId`, `GatewayConfig`. There is no `/v1/chat/completions`, no `/v1/audio/transcriptions`, no `/v1/audio/speech`. Verified by grep across `voicegateway/server.py` — no OpenAI-shaped endpoints exist.

The library API:
```python
gw = Gateway()
stt = gw.stt("deepgram/nova-3")
llm = gw.llm("openai/gpt-4.1-mini")
tts = gw.tts("cartesia/sonic-3:voice_id")
```

`gw.stt()/llm()/tts()` return **native LiveKit plugin instances** (`livekit.plugins.deepgram.STT`, etc.) wrapped transparently by `wrap_provider()` for instrumentation (`voicegateway/middleware/instrumented_provider.py`). They drop directly into `AgentSession(stt=, llm=, tts=)`.

**Switching cost from raw LiveKit plugins is 3 lines of code.** Switching cost from LiteLLM (HTTP) is 0 — they're different shapes. Switching cost from "no gateway, raw provider SDKs" is moderate but the YAML config payoff is real.

**The framing problem.** The README and `docs/index.md` call VG "a self-hosted inference gateway." That phrase, in 2026, primes readers to expect *an HTTP proxy with OpenAI-compatible endpoints* (LiteLLM's shape). Readers who land on the docs and discover it's a Python library with a LiveKit return type will recalibrate quickly *if* they're LiveKit users; non-LiveKit users will bounce. This is a substantial framing slip and a candidate for the headline rewrite.

**Verdict: 7/10 for LiveKit-agents users (clean integration, low switching cost). 3/10 for everyone else.**

### 4c. LiveKit-agents wiring

Native objects, transparent middleware wrapping (`voicegateway/middleware/instrumented_provider.py`). Cost tracking and latency measurement happen via attribute proxying without changing the LiveKit interface. This is the right architectural call — proxy mode would have meant maintaining HTTP shims for every provider.

The brittleness risk is LiveKit-version compatibility: VG pins `livekit-agents>=1.5.0` (`pyproject.toml:20`). If LiveKit changes the plugin protocol in a 2.x release, every provider wrapper here breaks at once.

**Verdict: 7/10 — clean architecture, single dependency that's also the moat.**

### 4d. Documentation completeness

60+ markdown pages under `docs/` (38,053 lines). Sections: `api`, `architecture`, `cli`, `configuration`, `contributing`, `examples`, `guide`, `mcp`, `migration`, `reference`. Index page (`docs/index.md`) leads with hero card and feature grid; quick-start (`docs/guide/quick-start.md`) covers the seven-step happy path; per-modality references in `configuration/`.

**Specific weaknesses:**
- `docs/guide/first-agent.md` does not include LiveKit server setup as a prerequisite (per DX/prod agent's read).
- `docs/migration/from-litellm.md:12-19` claims LiteLLM has no STT/TTS/MCP — *stale and wrong as of May 2026.* LiteLLM ships `/v1/audio/transcriptions` (Whisper, Deepgram, ElevenLabs Scribe) and `/v1/audio/speech` (OpenAI, Azure, Gemini, ElevenLabs). This doc undermines credibility on first contact with anyone who has actually evaluated LiteLLM.
- Code samples in some pages are runnable; others assume context (audio I/O sourcing is hand-waved in `quick-start.md`).
- No "common pitfalls" or "ops runbook" page.

**Verdict: 6.5/10. Surface is broad and well-organized; one critical staleness (the LiteLLM comparison) and a few examples assume implicit context.**

### 4e. Top 3 onboarding friction points

1. **LiveKit server setup is undocumented as a prerequisite** in the agent path (`docs/guide/first-agent.md`). New users who follow the doc verbatim will hit `ConnectionError: Failed to connect` and lose 10-30 min.
2. **`pip install voicegateway` (no extras) silently lacks providers.** A user who runs `voicegw status` after the bare install will see all providers unconfigured and may not realize they need `[cloud]` or specific extras like `[deepgram]`. The README example uses `[cloud,dashboard,mcp]` (line 61) but the migration guide doesn't reinforce this.

## Section 5 — Production readiness

### 5a. Auth on the HTTP API

`voicegateway/core/auth.py` (verified read of lines 1-60). Bearer token model:
- Disabled by default. With no `auth.api_keys` config and no `VOICEGW_API_KEY` env var, `/v1/*` is anonymous.
- `hmac.compare_digest` for constant-time comparison — correct.
- `ApiKey` carries scopes (`("read",)`, `("write",)`, `("*",)`); FastAPI dependency `require_scope("write")` is applied to mutating endpoints.
- CORS configurable via `auth.cors_origins`; default permissive.
- No OAuth/OIDC, no per-project keys (one global keyring), no key expiry/rotation.

`/health` and `/v1/metrics` are always public per the example yaml comment (`voicegw.example.yaml:192-193`) so load-balancers and Prometheus can scrape regardless of auth state.

**Verdict:** appropriate for self-hosted single-tenant; insufficient for SaaS or per-customer isolation.

### 5b. Multi-tenancy

Logical isolation only. `project` is a tag on requests and a key on `managed_projects`. All projects share the same Python process, the same SQLite DB, and the same provider connection pool. There is no resource isolation, no per-project rate limit, no per-project request timeout. A single misbehaving project (e.g., a runaway loop calling `gw.llm()` 1000x/sec) will affect every other project on the same instance.

The recommended deployment for true multi-tenancy is "one VG instance per customer" — operationally expensive and not documented.

**Verdict:** acceptable for internal-team multi-project; non-viable for SaaS isolation.

### 5c. Secrets handling

- Provider keys: `${ENV_VAR}` substitution in YAML is the documented pattern. Hardcoded keys in YAML work but are discouraged.
- Managed provider keys (added via dashboard or HTTP API) are Fernet-encrypted in SQLite (`managed_providers.api_key_encrypted`).
- Audit log redacts `api_key` before logging (per the conversation history's review fix).
- Fernet master key fallback to `~/.config/voicegateway/.secret` with mode 0600.

**Risks not yet addressed:**
- `VOICEGW_SECRET` env var passed through `docker run -e` is visible in `docker inspect` and `ps auxe`. No documented use of Docker secret mount or external secret managers.
- User-supplied request metadata fields are logged as-is into the `requests` table; if a user passes secrets in metadata they end up in SQLite plaintext. No documented warning.

**Verdict:** mostly correct primitives; documentation gap on secret-mount best practices.

### 5d. Scaling

SQLite single-writer; in-memory budget cache per process. Multi-instance behind a load balancer:
- Reads scale (SQLite reads can fan out, especially in WAL mode).
- Writes serialize through the SQLite file lock.
- Budget cache is independent per instance — overshoot bounded by `(N × cache_ttl × per-instance burst spend)`.

There is no Redis backend, no Postgres backend, no shared cache, no leader-election. The product is designed for single-instance deployment. The example `deploy/fly/fly.toml` uses a single shared-cpu-1x/512MB machine.

For users who hit a scaling ceiling, the migration path is undocumented and would be a substantial architectural project (introduce Postgres, refactor SQLite-coupled storage, add Redis-backed cache).

**Verdict:** single-instance is the supported and tested topology. Honest framing would be to say so explicitly.

### 5e. Deployment options

Documented and verified to exist:
- `pip install` — README covered.
- Docker single-image — `docker run mahimairaja/voicegateway:latest` (multi-arch via `docker-publish.yml`).
- Docker Compose — `docker-compose.yml` at root, compose example in README.
- Fly.io — `deploy/fly/deploy.sh` with one-command flow.

Not documented:
- Kubernetes (no manifests, no Helm chart).
- Systemd unit file.
- Bare Linux process supervision (e.g., supervisord).

CI tests every push via `ci.yml` and `test-coverage.yml`. `docker-publish.yml` builds multi-arch on tag push. `fly-deploy-validation.yml` runs `flyctl config validate`. The cost-deep-dive agent's claim of "no CI/CD" was wrong — CI exists and is comprehensive. (Correcting the record.)

**Verdict:** four well-supported paths, K8s as future work.

### 5f. Backup & restore

Not documented. SQLite at `~/.config/voicegateway/voicegw.db` (or the configured `db_path`); a user wanting backups today copies the file via cron. There is no `voicegw backup` command, no documented disaster-recovery procedure, no example for backing up the encrypted Fernet key alongside the DB. WAL mode is not explicitly set in the schema (would need verification of `PRAGMA journal_mode`).

For a self-hosted product, this is a real gap. The first time a user loses their data, the absence of a backup story will hurt.

**Verdict:** critical undocumented gap; one CLI command (`voicegw backup`) and a docs page would close it.

### 5g. Migration story between versions

Not documented and likely unimplemented. There is no `config_version` field in YAML, no Alembic-style schema versioning in `voicegateway/storage/sqlite.py`, no `voicegw migrate` CLI command. The project is at v0.0.3 with three releases; no version-to-version breaking changes have happened yet, so the absence is invisible. The first time a schema needs to change, users on the older version will need manual remediation.

**Verdict:** acceptable for v0.0.x; needs to be addressed before v1.0.

### Honest "Why VG over LiteLLM?" answer

Three differentiators hold up under code scrutiny:
1. **LiveKit-native return types.** `gw.stt()/llm()/tts()` produce LiveKit plugin instances that drop straight into `AgentSession(...)`. LiteLLM gives OpenAI-shaped JSON; you'd write a plugin shim. For voice agents on LiveKit this is a real ergonomic delta.
2. **Modality-aware unit accounting.** LiteLLM tracks tokens. STT is billed by audio-minute and TTS by character; `cost_tracker.calculate_cost` (`cost_tracker.py:55-63`) handles all three first-class. To replicate this in LiteLLM today you write per-modality custom callbacks.
3. **Project + MCP combo.** Per-project daily budgets with `warn`/`throttle`/`block` exposed to a coding agent through 17 MCP tools gives a workflow ("Claude, set Tony's Pizza to a $5/day budget on the premium stack") that LiteLLM has no equivalent for.

Where LiteLLM wins, it wins decisively: 100+ LLM providers vs 4, OpenAI-compat proxy that lets every existing OpenAI client work unchanged, five-level budget granularity, Postgres-backed fleet for horizontal scale, runtime-error-driven fallback (vs VG's resolver-only), and adoption signals dwarf VG by five orders of magnitude.

**Is "voice + LiveKit-native + local-model unification" enough wedge to displace LiteLLM in a developer's evaluation?** For the LiveKit voice-agent niche, yes. Outside it, no. The wedge is real but narrow, and is defensible only as long as (a) voice and LLM stay separate procurement decisions and (b) LiteLLM doesn't ship a LiveKit plugin or modality-aware cost units. Both could change in a sprint at LiteLLM's pace.

The README leads with "self-hosted inference gateway" (a phrase that primes readers to expect an HTTP proxy in the LiteLLM shape, which VG isn't) instead of "the gateway your LiveKit voice agent needs" (the actual defensible wedge). **Why I'm not picking other candidates:**

**Combined call: ship a launch, fix the framing, address the structural gap (`/v1/chat/completions` shim) only after the launch validates demand.** Don't pre-build for the broader audience; prove the LiveKit niche cares first.

### 1. Launch publicly with a tightened wedge narrative — within 2 weeks

**What.** Pair a README + `docs/index.md` rewrite that leads with "the gateway your LiveKit voice agent needs" with a coordinated launch: Show HN post, r/LocalLLaMA + r/voiceai + r/LiveKit posts, a Twitter/X thread, a 1500-word blog post on the LiveKit voice-agent use case (co-publish to dev.to and Hacker Noon), and a 5-minute screencast demoing "Claude, give me a $5/day budget on the premium stack and switch to local on outage." **Effort.** 1-2 person-weeks (most of it is the README + migration doc rewrite, the blog post, and the screencast).

**Risk.** Low. Launch reactions provide the highest-fidelity signal we'll get on whether the wedge resonates. The downside of a tepid launch is information; the upside is the first 100 stars and the first 10 issues from real users.

### 2. Ship runtime fallback, not just resolver-time fallback

**What.** Wire error-driven fallback into `InstrumentedSTT|LLM|TTS` (`voicegateway/middleware/instrumented_provider.py`) so a Deepgram timeout *during a call* triggers a swap to Groq Whisper (or local) without dropping the LiveKit session. **Why.** The README and `docs/index.md:48` explicitly claim "Cloud outage? Switch to local. Your agent keeps running." `voicegateway/middleware/fallback.py` only triggers on resolver failure, not on operational errors mid-call. This is the most overstated marketing claim. Closing the gap between claim and reality is essential before any post-launch attention forces sophisticated readers to test it.

**Effort.** 1-2 person-weeks. Timing-sensitive code on the voice-agent hot path; needs careful integration tests with simulated provider failures.

**Risk.** Medium. The hot path is on a phone call — a regression here is audible to the end user. Test rigor matters.

### 3. Add OpenAI-compatible HTTP shim for non-LiveKit users

**What.** Implement `/v1/chat/completions`, `/v1/audio/transcriptions`, and `/v1/audio/speech` in `voicegateway/server.py` as proxy endpoints that forward to the configured provider, run cost tracking, and respect project budgets. **Why.** Section 4b identified that VG is currently a Python library (with an admin API), not an HTTP gateway. Outside the LiveKit niche, this is invisible to the 90% of "LLM gateway" market that lives on the OpenAI HTTP shape. Adding the shim unlocks LiteLLM-style adoption *without* abandoning the LiveKit-native return types — both can coexist. This is the single largest addressable-market expansion available.

**Effort.** 2-3 person-weeks. Provider-by-provider request/response mapping is real work, and streaming over SSE adds complexity. Could be scoped to LLM-only first (`/v1/chat/completions`) and audio later.

**Risk.** Medium. Maintenance burden of the OpenAI shape vs the upstream provider drift; small surface, but real.

### 4. Cost-tracking reconciliation tooling

**What.** Add a `voicegw export-costs --start ... --end ... --format csv|json` CLI command that emits per-request line items with model_id, provider, project, units, calculated_cost, and timestamp. Add a `docs/examples/cost-reconciliation.md` page showing how to compare the export against an OpenAI invoice. **Why.** Section 2c found no reconciliation tooling at all. The wedge story ("trust us with your FinOps") is undermined every time a user has to write SQL against SQLite to verify a number. CFO-grade trust requires a one-command export.

**Effort.** 1-2 person-weeks. The CLI command is straightforward; the pricing-metadata update is trivial; the docs page is the bulk of the work.

**Risk.** Low. Net-additive feature, no changes to hot path.
